# PicaComic 后续优化方案

日期：2026-11-13。评估基线：`e0630631`，应用版本 `4.2.19+4219`。

## 1. 建议结论

下一轮优先解决升级、恢复和同步的数据一致性问题，随后优化阅读器调度、启动恢复和内存。架构调整随这些任务逐步进行。

当前已经具备下载取消与重试回归、图片任务所有权、50 MiB 原始图片 LRU、坏图缓存失效、分页请求代次隔离和网络日志脱敏等基础。已有修复不再作为新的优化任务重复安排。

本方案基于当前源码、测试和构建配置的静态核查。没有重新运行 Flutter 测试、设备测试、GitHub Actions 或性能采样；下文的风险不代表已经发生用户事故，性能收益也需要测量后确认。历史审计见 `docs/repository-audit-2026-11-13.md`，其中签名配置和应用版本的描述已有变化，以当前代码为准。

## 3. 具体实施方案

### O1：先写入并验证，再清理旧数据

**代码依据**：`lib/init.dart:96` 的 `_checkOldData()` 将旧 Cookie 加入局部 `cookies` 列表，随后在 `:150`、`:153`、`:157` 删除旧目录，整个分支没有将列表写入新 Cookie 库。外层迁移触发条件也没有单独覆盖只有旧 `cookies` 目录的情况。新库写入入口为 `lib/network/cookie_jar.dart:36`。

**触发与影响**：用户从仍使用旧 Cookie 目录的版本升级，且进入该迁移分支时，旧登录态可能被清理而未保存。是否存在这类用户数据需要用旧版本样本验证。

**实施步骤**：

1. 按来源 URI 收集 Cookie，保留 domain、path、secure、httpOnly、expires，写入新库的事务中。
2. 回读并校验迁移结果，成功后才记录迁移版本；旧目录先重命名为备份，经过成功启动后再清理。
3. 为账号迁移和数据库结构迁移建立显式版本号与幂等入口，避免每次启动执行破坏性检查。

**验收**：只有旧 `cookies` 目录、多个旧目录共存、空目录、写入失败和重复启动都可预测；失败保留原件，重复执行不丢数据、不重复增加记录。先用虚构账号和 Cookie 构造样本。

**回退**：保留原目录和旧版本可读数据；不在同一版本中立即删除迁移备份。

### O2：将备份恢复改为可验证、可回退的操作

**代码依据**：`lib/tools/io_tools.dart:291` 直接打包正在使用的数据库文件；`:406` 的 `importData()` 使用固定 `dataTemp`，在完整恢复完成前替换 `comic_source`、Cookie 文件和下载目录。最终设置校验在 `:504` 才执行。异常路径没有恢复已被替换目录的步骤。此外，过旧版本分支在 `:447` 返回 JSON，只跳过文件替换，后续仍会执行设置导入。

**触发与影响**：备份缺文件、设置格式无效、存储空间不足，或恢复中途终止，都可能留下部分新数据、部分旧数据的状态。正在写入的数据库被直接复制时，也需要验证快照一致性。

**实施步骤**：

1. 新备份增加 manifest：格式版本、应用版本、生成时间、文件清单、长度和摘要；继续兼容读取旧格式。
2. 导出数据库使用 SQLite backup API 或受控的一致性快照；若当前绑定不支持所需 API，先短暂串行化写操作再复制，不直接切换 WAL。
3. 恢复使用独立临时目录，先检查归档路径、文件数量、解压大小、必需文件、JSON 类型和数据库完整性；自动同步遇到过旧版本应整体跳过，手动恢复另行定义版本策略。
4. 校验通过后暂停写入，备份现有文件，按恢复日志逐步替换；跨多个文件的恢复不假设存在一次性的原子事务。
5. 任一步失败回滚；下次启动识别未完成的恢复日志并完成回退。临时文件清理失败不能覆盖原始错误。

**验收**：正常恢复保持收藏、历史、账号和下载；在各替换点注入失败或终止后，重启可以恢复完整旧状态或完整新状态。缺文件、坏 JSON、坏数据库、空间不足的输入不能先删除现有数据；自动同步跳过过旧版本时设置和文件均不变化。

**回退**：manifest 先作为新格式扩展；保留旧格式读取和恢复前快照，独立提交导出与恢复改动。

### O3：统一 WebDAV 的操作队列和版本提交时机

**代码依据**：

- `lib/network/webdav.dart:47` 在上传成功前修改本地同步版本；`:78` 未等待旧备份删除，`:84` 才上传新备份。
- 上传通过 `_isOperating` 等待，而 `downloadData()` 在 `:98` 直接设置该标记，上传和下载没有共同的串行入口。
- `lib/base.dart:268` 的 `writeData(false)` 仍调用默认参数的 `updateSettings()`，后者在 `:253` 触发上传；导入回调因此仍可能触发同步。
- `lib/network/webdav.dart:169` 在下载重试失败后改变配置字符串，使同步变为禁用状态，配置与运行状态混在一起。

**实施步骤**：

1. 上传、下载、恢复进入同一个串行协调器，返回可等待的 `Future<SyncResult>`；取消和失败统一在 `finally` 释放操作状态。
2. 将 `sync` 参数完整传递，明确“本地保存”与“请求同步”的边界。连续设置变更合并为一次待上传任务，成功后若仍有新变更再上传一次。
3. 优先上传唯一版本文件，确认成功后再提交本地同步版本、等待旧文件清理；服务器支持 MOVE 时可使用临时文件提交，不支持时采用可校验的版本文件。
4. 分开记录最近下载、最近上传和本地变更版本；用远端 ETag/条件请求或版本记录检测多设备冲突。先保留双方备份，不按设备时间无条件覆盖。
5. 临时故障保留配置，记录失败原因并允许重试，避免把网络失败写入配置格式。

**验收**：上传失败后上一份有效备份仍在；导入不会自动反向上传；并发上传/下载最多一个任务进入替换阶段；连续修改后最终状态确实上传；两设备同时修改不会静默丢弃一方备份。

**回退**：保留现有远端文件命名的读取兼容；新增同步状态单独保存，失败时不清理历史版本。

### O4：修正预加载标记，再调整预加载范围

**代码依据**：`lib/pages/reader/image_view.dart:440` 按 `logic.length` 检查标记数组，却在 `:441` 创建 `logic.length + 1` 项；全仓引用中没有将任一项设为已请求。`:448`、`:456` 的 `precacheImage()` 也没有接入任务结束与失败后的标记更新。

**影响边界**：可以确认标记未生效、会重复初始化和调度；Flutter ImageCache 与 ImageManager 仍可能合并请求，不能仅据此断言每次都会重复下载。

**实施步骤**：

1. 先明确 URL 的 0 基索引和阅读页码的 1 基索引，以完整章节身份和图片 key 管理预加载任务。
2. 请求入队前标记，成功、失败和取消后更新状态；遍历遇到已请求项时跳过该项，继续检查后面的候选图片。
3. 当前页优先，预加载限量；换章节、快速跳页和退出阅读器时取消不再需要的任务，复用现有 owner 机制。
4. 固定窗口通过测试后，再依据方向、网络和内存基线决定是否增加自适应预加载。

**验收**：相同章节位置连续触发 20 次，候选图片不会重复进入活动队列；失败可以再次预加载；跳页后当前页优先；单页、双页、首尾页及章节切换无越界。分别统计预加载调用次数与真实 HTTP 次数。

### O5：建立整机内存基线，逐步减少图片副本

**代码依据**：`lib/main.dart:161` 将 Flutter ImageCache 设为 200 MiB；`lib/foundation/image_loader/base_image_provider.dart:120` 另有 50 MiB 原始字节缓存；`android/app/src/main/cpp/pica_curl.c:79` 限制单个原生响应为 64 MiB，完整响应还会跨 JNI/MethodChannel 返回 Dart。以上限制都不是进程总内存上限，不能简单相加得到 RSS。

**实施步骤**：

1. 用固定图片集分别采集 Dart heap、native heap、进程 RSS/PSS、解码尺寸、首图时间、缓存命中率和帧耗时。
2. 对比原始字节缓存和解码缓存的命中收益，再调整预算；明确大图、长条图、后台运行和内存压力下的淘汰策略。
3. 缩略图按显示尺寸解码，阅读原图保留放大质量；避免用统一低分辨率处理所有图片。
4. 若证实原生桥接副本是主要峰值来源，试点原生下载至临时文件或受控分块通道，接入现有缓存提交和取消清理；保留响应大小限制。

**验收**：在同一设备、同一图片集和并发数下比较峰值内存与首图 p95；连续阅读、退回、再次进入至少 10 轮，内存释放后的趋势不持续增长。是否接受具体内存预算，由首轮实测决定；不预先承诺降低比例。

**回退**：缓存预算独立配置；新的原生图片传输路径先局部启用，保留原路径用于对照。

### O6：设置可靠落盘，启动失败可恢复

**代码依据**：`lib/base.dart:176` 直接解析 settings 文件，`:251` 直接覆盖写入；`:169` 的 `setSearchMode()` 仍将整份 settings 写入 SharedPreferences，而读取优先使用文件。`lib/init.dart:90` 捕获初始化异常后仅记日志，`lib/main.dart:35` 等待 init 返回后仍继续启动业务界面。

**实施步骤**：

1. P1：设置写入串行化，在同目录写临时文件、flush 后替换并保留备份；启动校验类型、长度和枚举范围，读取失败时提供备份恢复路径。
2. P1：将 `setSearchMode()` 等入口统一到现有持久化路径，返回可等待的 Future；同步触发在成功落盘之后执行。
3. P2：从现有 `_Settings` 包装层逐步增加具名字段和校验，先覆盖阅读、代理、同步设置，保留旧数组格式的迁移能力。
4. P2：初始化返回明确结果，区分核心数据不可用与某个漫画源不可用；核心失败进入可重试的恢复界面，单源失败按源降级。
5. 先测量启动各阶段耗时；确认非首屏依赖后，再延迟标签翻译、清理及非当前源的准备工作，保留必要依赖顺序。

**验收**：截断 settings、非法数字和写入失败不会静默破坏原文件；搜索排序重启后保留；核心初始化失败不进入依赖未初始化对象的页面；单源失败时本地收藏和下载仍可用。

**回退**：先统一读写与恢复逻辑，再迁移字段表示；新版本过渡期持续读取旧格式。

### O7：限制原生并发，保持超时与代理切换语义一致

**代码依据**：`android/app/src/main/kotlin/com/github/pacalini/pica_comic/MainActivity.kt:26` 使用 `newCachedThreadPool()`，原生入口没有独立的并发上限；`lib/network/app_dio.dart:117` 的请求拦截器统一覆盖超时；`AppHttpAdapter.fetch()` 在代理签名变化时强制关闭现有 adapter；`lib/network/native_curl.dart` 将各阶段超时折叠成一个原生超时。

**实施步骤**：

1. 为原生网络入口增加有限工作线程和有界待处理队列，队列中的任务也能取消；根据实测选择上限，不随线程池默认值扩张。
2. 显式区分连接超时、读空闲超时和总时限；尊重调用方的明确配置，再验证 Dart HTTP/1、HTTP/2 和 native curl 的对应行为。
3. 代理切换后让新请求使用新 adapter；对旧 adapter 实现有限期排空或明确取消，避免隐式影响其他在途请求。
4. 保留 GET/HEAD 可重试、POST 不自动重放、证书错误不降级及 owner 定向取消的现有规则。

**验收**：100 个虚构本地请求下活动线程和队列长度有界；队列取消最终释放资源；慢响应与连接失败分类正确；切换代理时旧请求的结果或取消原因可解释，无重复提交。

### O8：数据库先补事务和分页，再评估结构调整

**代码依据**：`lib/foundation/local_favorites.dart:345` 的表重建使用复制、删表、建表、回填等语句，外层没有显式事务；`:611` 的跨文件夹列表逐表读取全部记录。`lib/foundation/history.dart:399` 的 `getAll()` 全量按时间排序，SQLite 同步调用运行在当前 isolate。

**实施步骤**：

1. 表结构迁移显式使用事务与版本标记，失败回滚；批量导入与排序更新合并事务，减少逐条提交。
2. 构造 1 万、10 万条历史和多文件夹收藏数据，测量列表读取、跨文件夹搜索和导入耗时。
3. 对热点查询采集 `EXPLAIN QUERY PLAN`，再添加 time/display_order 等实际需要的索引；列表使用稳定排序和分批加载。
4. 只有测量证明同步 SQL 造成可见帧阻塞时，才将对应连接和操作整体迁到工作 isolate；不跨 isolate 直接传数据库句柄。
5. 暂不将“一个收藏夹一张表”整体迁移为新模型；只有跨收藏夹查询成为主要瓶颈，才另写兼容迁移设计。

**验收**：迁移中断后原表仍可读；导入幂等；大数据列表分页不丢项、不重复；保留查询计划和帧耗时前后对比。没有实测前不将这些静态特征认定为已发生卡顿。

### O9：统一构建输入，验收实际平台能力

**代码依据**：Android 和 iOS Simulator 固定 Flutter `3.44.0`，Linux、iOS/macOS workflow 跟随 stable，README 仍标为 `3.41.6`。`pubspec.yaml:66` 的 Git 依赖跟随 main，`:106` 的打包依赖未指定 ref，部分包使用 any；现有 lockfile 已锁住解析结果，因此不是“每次构建必然漂移”。

Android 当前允许缺少自定义签名时回退默认签名，缺少预期证书时跳过比较；这是最近提交明确采用的行为。`android/app/src/main/cpp/CMakeLists.txt:10` 只为 arm64-v8a 接入 libcurl，其他 ABI 即使产出 APK，也不代表具备同样的原生代理网络路径。

**实施步骤**：

1. 统一 Flutter 版本来源并同步构建说明；对关键依赖补充约束，Git 依赖固定到已验证提交，CI 使用 `flutter pub get --enforce-lockfile`。
2. Android 保留现有分析、Flutter 测试和 native curl 测试；确认 lib/test 无 warning 后恢复 warning 导致 CI 失败，info 使用可追踪基线分批减少。
3. 为 Linux、iOS/macOS 增加定期或相关路径变更触发的构建冒烟；若继续支持 Windows，补 Windows 构建任务。
4. 每个发布产物记录应用版本、commit、Flutter/engine、ABI 和实际证书摘要；保持现有可选签名策略，并用连续两个发布包验证覆盖升级和数据保留。
5. 对 arm64-v8a、armeabi-v7a、x86_64 分别标明原生 curl 能力和回退路径，以真实安装/网络冒烟决定是否补齐其他 ABI 的库。
6. 将 README/INSTALL 的下载链接与 `lib/network/update.dart:5` 当前发行仓库统一，避免安装说明与应用更新指向不同仓库。

**验收**：干净 runner 能按锁文件完成解析和构建；每种声明支持的 ABI 都有能力记录；签名比较关闭时仍能知道产物证书；前后版本能够覆盖安装或明确报告证书不兼容。此处不假设远端 secrets、签名连续性或设备验收已经完成。

### O10：按行为边界拆分，补关键集成回归

**代码依据**：`lib/foundation/image_manager.dart` 约 1025 行，`lib/foundation/local_favorites.dart` 约 1002 行；网络、缓存、源适配和持久化存在集中实现。现有 `test/` 已覆盖多种取消、分页、日志、索引和图片缓存回归，本轮未检索到旧 Cookie 迁移、完整备份恢复、WebDAV 协调及阅读预加载的专门行为测试。

**实施方式**：只在 O1-O9 修改对应行为时提取必要入口，例如迁移协调、备份恢复、同步协调、预加载调度。复用 Dio adapter 注入、本地 HTTP 服务和临时目录的现有测试方式；测试中恢复 singleton/global 状态，避免用例互相污染。

**验收**：测试覆盖成功、失败、取消、重试和重启恢复；解析 fixture 覆盖 API/HTML 正常及异常响应；CI 不依赖真实账号或外站。模块拆分前后的既有回归一致，不以代码行数下降作为交付指标。

## 4. 推荐推进顺序

### 第一批：数据可靠性，约 7-12 人日

1. 固定迁移、备份、同步的虚构数据样本；用失败测试锁定 Cookie 未写入、`writeData(false)` 仍触发上传、上传前清理旧备份三个行为。
2. 完成 O1、O3，以及 O6 中设置可靠落盘与统一写入入口；用稳定的本地保存边界支持后续恢复操作。
3. 完成 O2：先一致性导出，再校验恢复与回滚；按替换点做故障注入和重启验收。

退出条件：升级和同步不丢旧数据；恢复失败可回退；导入不触发意外上传；既有取消、分页和图片回归通过。首批不做数据库模型变更。

### 第二批：阅读与性能，约 6-10 人日

1. 完成 O4，并统计预加载候选数、入队数和真实请求数。
2. 建立 O5 的整机基线，选出最主要的内存来源；根据数据决定是否改造原生传输。
3. 推进 O7 和 O6 的启动降级；O8 先完成迁移事务，再按实测决定分页和索引范围。

退出条件：相同请求不会重复排队；并发和资源使用有界；首图、翻页和启动数据可对比。只保留收益经验证且质量无回退的性能改动。

### 第三批：持续治理

O9 的版本统一、锁文件验证可在前两批穿插完成；各平台和覆盖升级验收按支持范围执行。O10 随功能修改进行，不单独启动全仓重写。各批估算为优先试点范围，完整实现表中全部方向需另行按验证结果细化工期。

## 5. 验证与交付标准

| 场景 | 最小验证 | 交付证据 |
| --- | --- | --- |
| 升级 | 旧目录单独存在、多来源 Cookie、写入失败、重复启动 | 新库结果与旧目录保留情况 |
| 备份恢复 | 正常、缺文件、坏格式、空间不足、阶段性进程终止 | 恢复日志、数据库完整性、目录前后清单 |
| 同步 | 失败重试、上传下载并发、连续修改、双设备冲突 | 请求顺序、版本记录、旧备份仍可恢复 |
| 阅读 | 重复触发、快翻、双页、换章节、退出再进入 | 实际请求计数、owner 清理与页面结果 |
| 性能 | 固定图片集，大图与长条图，阅读加后台下载 | RSS/PSS、heap、首图与帧耗时的前后对比 |
| 数据规模 | 1 万/10 万历史、多文件夹收藏 | SQL 查询计划、耗时、分页完整性 |
| 发布 | 干净构建、各 ABI 冒烟、连续版本覆盖安装 | 构建日志、产物摘要、实际证书与数据保留结果 |

性能采样使用相同设备、系统、profile/release 模式、图片集和并发数，区分冷缓存与热缓存。启动和首图每组建议至少 20 次，报告中位数、p95、样本数及离散情况；采样不足时不作稳定性结论。所有阈值在取得基线后制定。

每项优化独立提交，附触发条件、修改范围、回归结果和回退方式。优先验证可观察的行为，不以“测试数量增加”“大文件变小”或“依赖更新”为完成标准。

本轮只新增方案和对应工作记录，没有修改业务代码、工作流、依赖、版本号，也没有执行提交、推送或发布。
